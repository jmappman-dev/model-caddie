# Changelog

## 0.2.0 (2026-09-23)

The review pass now fires on code CHANGES, not only on the word "review", and independence is judged per provider rather than per model.

- The review pass has a second trigger: a task that CHANGES code now requires it, even when the text never says "review". Keying only on that word meant a bug fix or a new script, exactly the code an outside pass exists for, required nothing, so the requirement rested on whoever remembered it. Detection keys on signals that survive filename stripping (test, TDD, crash, traceback, refactor) because the path and extension that would otherwise mark a task as code work are removed before matching.
- The review pass carries a `scope`: `security` when the task touches credentials, auth, money, PII, untrusted input or public reachability, otherwise `correctness`. A security scope adds a note telling the reviewer's prompt to look at credential leakage paths, trust boundaries, authorization fail-open behavior, blast radius and the third-party trust chain. A correctness-scoped prompt reliably misses that class of defect.
- Independence is now provider-level. The reviewer-selection guard compared `[provider, model]`, so a second lane on the SAME provider with a different model passed it and the run reported an "independent review pass" that was not one. Two models from one vendor share training data, tooling and blind spots. Such a lane is now refused with a reason naming the clash, and the requirement stays, asking for a manual second pass.
- `reviewPass.scope` is recorded in the JSONL decision log, and the CLI prints it on the `review pass (...)` line.
- Widening WHEN the pass fires does not widen cost: the tier ladder still keys on the original review matcher, so a code fix routes to the same model it did before and simply carries the pass.
- Trivial edits (typo, rename, reformat), prose and content work, read-only investigation, and ordinary bookkeeping still require no pass.

- Naming a source file or a source directory path is itself evidence of code work. This is detected on the RAW task text, before filename stripping, because stripping removes the path and extension that prove a task is code and no keyword list can recover it afterwards. Prose and tabular files (md, txt, csv, pdf, xlsx, log) are deliberately excluded: editing a README is not code work.
- A trivial mechanical edit still requires no pass even in a named source file, because a typo fix in a .go file is noise. Real code evidence elsewhere in the same task overrides that, so "fix the parser and rename the helper" keeps its pass.
- Provider comparison normalizes to a vendor root before comparing, so `openai` and `openai-codex` or `openai_codex` are correctly refused as a reviewer pair. See docs/CONFIGURATION.md for the one direction this deliberately over-matches, and why that direction is the safe one.

Four independent Codex review rounds ran against this change before release, and every round found real defects in it. The first found that a trivial keyword anywhere (`rename`, `reformat`) cancelled the review requirement for a substantive fix, that business vocabulary alone made ordinary bookkeeping demand a security code review, that the `sanitize` and `sanitise` matchers never matched the actual words, and that provider equality compared raw labels. The second found the first two only partially closed, and caught that tightening the keyword list had opened a worse hole than it shut: with bare `bug`, `test`, `helper` and `timeout` gone, `fix the bug in src/retry.js` required no review at all, because stripping had removed the only remaining evidence. That is what the raw-text source-file check fixes. The third found that the source-file check had in turn created its own false positives, with two concrete regex defects: the directory matcher accepted any leaf, so `src/README.md` read as source, and a trailing word boundary matched the `.js` inside `retry.js.md`. It also showed that data, config and markup extensions were too weak to treat as conclusive code evidence, that a named source file was wrongly attaching a pass to a live-fact lookup, and that the trivial-edit guard had become dead code. All fixed. A fourth round was not run: the loop was stopped by judgment, not because it had converged to zero findings.

Measured rather than asserted. This release adds `eval/`: a labeled corpus, two blind holdout sets written by an outside reviewer from the contract alone, and `npm run eval`, which reports precision, recall, a confusion matrix and per-slice results, with a release gate that weights recall above precision on purpose.

That harness immediately changed the picture. The classifier scored 100% on the maintainer's tuned corpus and **58.8% precision / 33.3% recall** the first time it met a blind set, which is what overfitting looks like from the inside. The blind sets then surfaced defects that four independent code reviews had all missed: a sentence-ending full stop stopped a source filename being recognised at all; review requests phrased with any words between the determiner and the noun matched nothing; imperative English the verb list had never heard of ("make", "turn", "teach", "keep", "swap"); tickets written as noun phrases with no verb at all; and ASCII-only filename matching that made every non-Latin path invisible. A third blind set, written to a deliberately different distribution and run ONCE with no tuning afterwards, is the clean measurement: **68.8% precision, 55.0% recall, 61.1% F1, 72.7% scope accuracy** over 80 cases. Each of the three blind sets scored near 60 to 70% precision on first contact, rose above 90% after being used to fix things, and was then replaced by a fresh set that landed back near 60 to 70%. The tuned 100% is a regression suite, not quality. On the cleanest set the errors lean toward MISSING reviews (18) rather than over-requesting them (10), so the review pass is a useful prompt and not a guarantee. `eval/holdout3.json` is deliberately left unburned as a clean gate for the next person. See [docs/KNOWN-LIMITATIONS.md](docs/KNOWN-LIMITATIONS.md) for every remaining failure class with a worked example, and for why the error balance leans the way it does.

Path-based forced review. A task naming a high-risk path (migration, auth module, dependency lockfile, CI pipeline, infrastructure definition, secret store) forces the review pass outright and the scoring cannot override it. Exempted only by an explicit read-only statement. Added on an arbitrated recommendation after a prior-art survey, on the reasoning that a path survives paraphrase where prose does not.

Its measured effect on the clean holdout is NONE: the rule fires on 1 of 80 cases there and every headline figure is unchanged. It costs 1 false positive on a second set, because a comment typo in an auth module now forces a review, which is deliberate. The value is real but narrow and demonstrated by 14 targeted tests rather than by the blind measurement. Stated plainly because claiming an improvement it did not produce would repeat the overfitting this release exists to document. The first version of the rule also violated its own design principle by accepting bare filenames, which a blind set caught firing on prose; it now requires a real path.

Also added: property and metamorphic tests (`test/properties.test.js`) covering determinism, cross-call state leakage, output validity on hostile input, bounded execution at the input cap, and transformations that must or must not change the answer.

Known limitations, stated as they actually behave rather than as intent. There is no investigation guard: detection keys on a mutation verb appearing anywhere, so a read-only request that merely describes a change ("explain how to fix the parser, do not change any files") still requires a pass. The cost is a redundant review recommendation, never a missed one. Filename and boundary matching is ASCII, so a non-ASCII source filename is not recognised as source. A fourth Codex round found both, along with a routing regression (a newly recognised source extension was not in the stripping list, so its filename words leaked into lane selection and sent a bug fix to the research lane), missing ordinary edit verbs (remove, update, delete, replace, revert), a negated trivial instruction cancelling substantive work, the content guard overriding explicit source evidence, and only the first source-directory candidate being examined. All six of those are fixed. The two limitations named at the start of this paragraph are not.

## 0.1.0 (2026-09-22)

First public release.

- Deterministic rule ladder (R1 override, R2 consensus, R3 live fact, R3b review, R4 large input, R5 tier ladder), no model call needed to pick a model.
- Capability lanes: primary, research, large-context, reviewer.
- Independent review pass on code, security, and spec reviews, with a configurable reviewer, tie-breaker, and fallback. With no second model available it asks for a manual second pass instead of disappearing.
- Negation-aware overrides: "don't use X" bars that lane for every later rule.
- Provider-agnostic JSON config with bundled profiles: anthropic, openai, google, ollama, claude-code-only.
- Lanes that need an API key fall back to the primary lane, naming the missing env var, when the key is not set.
- Append-only JSONL decision log, with an option to keep task text out of it.
- Hardened before release after an independent Codex review and a security review: the log is confined to a .jsonl file inside the working directory (symlinks included) and never appends to a non-log file; task text is left out of the log by default and always when it looks sensitive; provider, model, and dispatch strings cannot carry shell syntax or control characters; long or hostile task text is capped at 4000 characters and every pattern runs in linear time; unknown CLI flags are errors; the CLI names the config it used on every run.
